Rules the team learnt the hard way are written as tests that read the source code and refuse to pass if the rule is broken again. There are twenty-nine of them, and many were born from a bug that shipped.

### Prove it bites

A test that asserts an absence passes trivially if it is looking in the wrong place. So the contributor guide's rule for writing one is to prove the guard bites: plant the fault first, watch the test fail, then take the fault out. Most guards carry their own check that the scan is not vacuous.

### The kinds of thing they catch

Some guard the architecture: the Firebase boundary, database writes wrapped in the error mapper, no display text inside a port. Some guard the screen: no raw colour, no left or right geometry that would break under Arabic, no hand-written sign in front of money, and no sign left without its isolate when it is chosen in a condition or written before any figure. Some guard the books: returns never subtracted twice, no currency arithmetic in a widget, every stock run flushed, and month, year, drawer and day-ledger figures that never read the wall clock. And some guard the language: ledger notes stored in English, every category shown through its label, the Arabic file's contract checked forever.

  Twenty-eight guards live in test/architecture, the twenty-ninth beside the security tests, and all run with the rest of the suite. Beside them, a pre-pull-request script is the authoritative floor. It checks that generated code is fresh and that the translation files and catalogue are in step. It runs static analysis, the tests and the security-rules suites on the emulators. It flags conventions such as edits to protected paths or a missing version bump. Continuous integration runs the same script on pull requests into the release branch.
