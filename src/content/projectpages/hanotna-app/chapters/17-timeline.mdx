### How a change gets in

Every substantial change starts as an issue on a board before any code is written. A ticket is not built until it has passed a readiness gate of brainstorm, specification and plan. One branch per issue, a pull request into the development branch, and the owner merges every one. A milestone is a release and a scope contract: new work mid-milestone waits for the next one.

### What the history is made of

2,875 commits, 371 pull requests merged, twenty tags, and about 99 per cent of commits following one message convention. Tests and documentation together outnumber feature commits. Sixty-seven fixed bugs each have a write-up kept in the archive, because the reason behind a non-obvious line is worth more than the line.

### Releases, for shopkeepers

A release is built and sent through Firebase App Distribution to a testers group and then to the shop. Its notes are written for the people behind the counter, in sections for what is new, what changed and what was fixed, each fix described by its effect at the till.

  Commit types over the history: 647 features, 429 tests, 400 documentation, 366 fixes, 311 refactors, 260 chores. A version milestone's major bump is its final commit. Release engineering keeps the three Firebase configurations out of version control and signs release builds with a key the repository never sees.
